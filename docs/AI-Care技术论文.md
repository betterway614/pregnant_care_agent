# 基于AMD Ryzen AI平台的端侧孕期智能管理Agent系统设计与实现

## 摘要

围产期医疗管理面临医护人员配比不足、高危妊娠筛查滞后、患者隐私保护困难等多重挑战。本文提出AI-Care——一种基于AMD Ryzen AI Max+ 395异构计算平台的端侧孕期智能管理系统。系统采用"通用大语言模型+专科评估算法"的双引擎架构，通过CPU+GPU+NPU协同调度实现全链路本地化推理：GPU承载大语言模型推理（Qwen3.6-35B-Q8-VL），NPU执行胎儿生长受限（FGR）专科评估（ResNet18DualFusion ONNX），CPU负责任务编排、规则引擎和自然语言理解。在智能体设计层面，系统构建了面向孕妇、护士、医生三端的多Agent协作体系，基于Agno框架实现意图驱动的工具路由、结构化输出与多步推理闭环，并设计了三层医疗安全防护机制。实验结果表明，本地Q8量化模型在流式场景下首Token延迟仅0.34秒，吞吐量达53.70 tok/s；FGR评估端到端延迟控制在5秒以内；系统整体功耗不超过120W。该系统为医疗垂直领域的端侧AI Agent部署提供了可复用的技术范式。

**关键词**：端侧AI Agent；孕期管理；异构计算；大语言模型；胎儿生长受限；AMD Ryzen AI；量化推理

## 1 行业背景与问题定义

### 1.1 围产期医疗管理现状

围产期保健是降低孕产妇死亡率和新生儿不良结局的关键环节。世界卫生组织（WHO）数据显示，全球每年约有29.5万孕产妇死亡，其中超过50%与产前保健质量不足直接相关[1]。在中国，随着三孩政策全面实施，高龄产妇比例显著上升，妊娠期高血压疾病、妊娠期糖尿病、胎儿生长受限（FGR）等高危妊娠发生率持续攀升。

当前围产期管理面临四重矛盾：

**人力瓶颈。** 一名护士通常管理50-100名孕妇的随访、数据录入和异常筛查，人工效率导致高危信号识别滞后。

**筛查依赖经验。** FGR发生率3%-7%，是围产儿死亡第二大原因[2]。传统筛查依赖超声医师主观判断，缺乏系统化图像分析辅助工具。

**数据孤岛。** 孕妇自测、护士随访、医生诊疗三环节信息传递依赖纸质或分散系统，难以形成健康管理闭环。

**隐私与便利矛盾。** 孕期健康数据属于高度敏感的个人医疗信息。云端AI服务虽然计算能力强，但数据外传带来的隐私泄露风险在医疗场景中不可接受。

### 1.2 端侧AI的机遇

AMD Ryzen AI Max+ 395集成XDNA 2 NPU（50 TOPS INT8算力）、Radeon 8060S GPU（RDNA 3.5）、128GB LPDDR5x UMA内存，使单一消费级平台运行35B参数模型成为可能，为"数据不出端"部署提供硬件基础。

### 1.3 问题定义

如何在单一AMD Ryzen AI Max+ 395端侧平台上，构建覆盖"孕妇-护士-医生"三端的孕期智能管理Agent系统，实现大语言模型通用推理、专科评估算法、多Agent协作调度的全链路本地化运行，满足医疗场景对隐私保护、推理延迟和安全防护的严格要求？

目标：
- 端到端对话延迟P99 $< 3$s
- FGR评估延迟 $< 5$s
- 系统功耗 $\leq 120$W
- 全部数据不出端

## 2 系统总体架构

### 2.1 四层架构

```
┌─────────────────────────────────────────────────────────┐
│  表示层  │ 孕妇端(小程序) │ 护士端(Web) │ 医生端(Web)   │
├─────────────────────────────────────────────────────────┤
│  应用层  │ Agent管理 │ 排程服务 │ 随访服务 │ 规则引擎    │
├─────────────────────────────────────────────────────────┤
│  AI推理层│ GPU: LLM推理  NPU: FGR评估  CPU: 调度+NLU  │
│          │           UMA 128GB 统一内存                  │
├─────────────────────────────────────────────────────────┤
│  存储层  │ PostgreSQL+pgvector │ Redis │ 本地文件系统    │
└─────────────────────────────────────────────────────────┘
```

**表示层**：孕妇端采用移动端应用；护士端和医生端采用Vue 3 + TypeScript + Element Plus构建的Web应用。实时通信通过WebSocket实现，支持流式Token输出和即时预警推送。

**应用层**：基于FastAPI异步框架，包含Agent管理器、排程服务、随访服务、预警规则引擎、对话管理、报告生成等模块。

**AI推理层**：部署在AMD Ryzen AI Max+ 395上，通过UMA统一内存实现CPU/GPU/NPU协同。GPU负责LLM推理（Qwen3.6-35B-Q8-VL）；NPU负责FGR评估（ResNet18 ONNX）；CPU负责任务调度、规则引擎和NLU（正则匹配）。

**数据存储层**：PostgreSQL + pgvector为主数据库，Redis为缓存，本地文件系统用于影像归档。所有数据存储在本地。

### 2.2 三端Agent协作

| Agent | 角色 | 核心能力 |
|-------|------|---------|
| 小安 | 孕妇 | RAG知识问答、健康数据录入、情绪陪伴、紧急检测 |
| 小护 | 护士 | 自动随访生成、SOAP记录、高危筛查、问题上报 |
| 智医 | 医生 | FGR评估看板、鉴别诊断、AI医嘱、预警审核 |

三端通过Agno Team的Route协调模式自动路由，共享16个医疗工具，通过意图驱动的工具路由按需加载子集。

### 2.3 推理管线时间预算

以一次完整的孕妇对话为例，目标总延迟 < 3s：

| 阶段 | 时间 | 执行单元 | 说明 |
|------|------|---------|------|
| 接收请求 | 0ms | CPU | FastAPI路由 |
| NLU意图识别 | 10-50ms | CPU | 规则引擎正则匹配，<1ms |
| Prompt组装 | 80-85ms | CPU | System + Context + User |
| LLM推理 | 85-2800ms | GPU | Q8量化，首Token ~300ms |
| 后处理 | 2800-2850ms | CPU | 安全过滤、来源标注 |
| **总计** | **~2850ms** | - | **目标 < 3000ms** |

关键优化：CPU NLU（<1ms）与GPU LLM预填充流水线并行；KV Cache预分配（30GB预留）；系统Prompt GPU侧缓存。

## 3 模型与智能体设计

### 3.1 大语言模型：Qwen3.6-35B

系统采用"云端+本地"双模式部署，通过`LLM_MODE`环境变量切换，业务代码零修改。

**云端**：阿里云DashScope平台的Qwen3.6-35B-A3B，MoE架构每次激活3B参数，吞吐129.41 tok/s。优势在于高吞吐，但存在数据外传风险和API成本。

**本地**：Qwen3.6-35B-Q8-VL，Q8_0量化（GGUF），通过llama-server部署在AMD ROCm GPU上，约35GB显存，吞吐43.45 tok/s。实现完全数据本地化。

模型推理采用OpenAI兼容API协议，通过统一的`LLMClient`抽象层实现云端与本地的透明切换。

### 3.2 FGR评估模型：ResNet18DualFusion

#### 3.2.1 模型架构

FGR评估采用双分支融合架构，同时捕获胎盘图像的低级纹理特征和高级语义特征：

```
输入: 224×224 RGB (ImageNet归一化)
  ├─ 浅层分支: ResNet18 layer2 → AdaptiveAvgPool → 256d (纹理/边缘)
  └─ 深层分支: ResNet18 layer3+4 → AdaptiveAvgPool → 384d (组织结构)
拼接 → 640d → MLP(640→256→64→1) → sigmoid → 风险概率
```

分类器MLP结构：`Linear(640, 256)` → ReLU → Dropout(0.5) → `Linear(256, 64)` → ReLU → Dropout(0.25) → `Linear(64, 1)` → squeeze。

#### 3.2.2 训练策略

模型采用5折分层交叉验证训练，每折使用独立的ResNet18骨干网络（非预训练权重）。最终预测通过5折模型的概率均值集成。各折权重为 $[0.55, 0.70, 0.20, 0.85, 0.65]$，反映了各折在验证集上的相对性能。

#### 3.2.3 辅助特征融合

系统设计了基于手工特征的SVM辅助分类路径。从胎盘超声图像中提取20维手工特征：

- **灰度统计特征**（8维）：原始图像的均值、第50/75/90百分位数、峰度、四分位距，以及CLAHE增强后的标准差和均值
- **纹理特征**（12维）：LBP在半径1/2/3下的均值、标准差、熵，以及CLAHE增强后的百分位数特征

SVM采用RBF核函数，融合公式为：

$$p_{\text{fused}} = w \cdot p_{\text{resnet}} + (1 - w) \cdot p_{\text{svm}}$$

其中 $w$ 为各折的融合权重。当前版本中SVM融合暂时禁用（`USE_SVM=False`）。

#### 3.2.4 胎盘分割预处理

使用nnU-Net v2[3]对NT超声图像进行胎盘分割。采用2D配置，5折集成推理，生成胎盘掩膜后与原始图像配对送入分类器。掩膜二值化阈值为127（0-255尺度），最小有效面积为100像素。

#### 3.2.5 置信度分层

模型输出概率通过分层阈值映射为置信度等级：

| 概率区间 | 置信度 | 含义 |
|----------|--------|------|
| $p \geq 0.7$ 或 $p \leq 0.3$ | 高置信 | 可直接参考 |
| $p \geq 0.6$ 或 $p \leq 0.4$ | 中等置信 | 需结合临床 |
| 其余 | 低置信 | 建议进一步检查 |

### 3.3 智能体框架设计（Agno）

#### 3.3.1 意图驱动工具路由

系统设计了意图驱动的工具路由机制：用户消息先经NLU引擎分类意图，再加载对应Agent变体和工具子集。以孕妇Agent为例：

| 变体 | 工具数 | 调用上限 | 适用场景 |
|------|--------|---------|---------|
| chat | 3 | 3 | 日常闲聊、问候 |
| record | 4 | 4 | 健康数据录入 |
| qa | 3 | 4 | 知识问答 |
| emergency | 2 | 1 | 紧急情况处理 |
| main | 10 | 8 | 复杂查询（兜底） |

护士Agent和医生Agent各有5个类似变体。这种设计使简单对话仅需3个工具描述，复杂分析才需完整工具集，有效降低平均Token消耗。

#### 3.3.2 医疗工具库

系统定义了16个@tool装饰的医疗工具，按功能分为7组：

- **NLU工具**（2个）：`agno_parse_nlu`（意图/实体/情感提取）、`agno_check_emergency`（紧急检测，`stop_after_tool_call=True`）
- **规则引擎**（1个）：`agno_evaluate_vital_rules`（12个数值参数的高危规则评估）
- **健康数据**（2个）：`agno_save_health_data`（保存8种指标）、`agno_get_patient_context`（获取患者上下文）
- **记忆查询**（2个）：`agno_should_ask_weight`、`agno_should_ask_bp`
- **趋势分析**（1个）：`agno_analyze_health_trends`（14天趋势分析）
- **知识检索**（1个）：`agno_search_knowledge`（知识库检索，当前为关键词匹配，规划向量检索）
- **心理筛查**（1个）：`agno_get_epds_result`（EPDS评分解读，4个风险等级）
- **护士专用**（3个）：`agno_query_patient_data`、`agno_create_followup_record`、`agno_report_issue_to_doctor`
- **医生专用**（4个）：`agno_analyze_patient_comprehensive`、`agno_generate_medical_order`、`agno_handle_issue`、`agno_query_clinical_guideline`

#### 3.3.3 多Agent团队协作

"AI-Care孕期护理团队"采用Route协调模式，根据用户查询性质自动路由：

- 日常健康咨询 → 小安
- 护理分析、随访 → 小护
- 医学分析、风险评估 → 智医
- 紧急情况 → 直接提供急救指导，不路由

#### 3.3.4 工作流编排

**产检流程工作流**（4步）：健康数据采集 → 风险评估 → Router（常规/高危/紧急）→ 报告生成。

**预警分析工作流**（2步）：护士护理分析 → 医生预分析。

#### 3.3.5 结构化输出

系统定义了8个Pydantic输出模型，关键模型包括：

- `NurseAnalysisOutput`：摘要、风险评估、护理建议、随访重点
- `DoctorAnalysisOutput`：分析、证据参考、建议医嘱、风险摘要、鉴别诊断（含支持/反对依据）、推理链
- `FollowUpGenerateOutput`：开场白、问题清单（4-6个含目的的问题）、结束语
- `FollowUpAnalysisOutput`：温暖总结、异常指标、趋势分析、个性化建议、护士行动建议

### 3.4 三层医疗安全防护

```
第1层 [前置钩子] EmergencyGuardrail
  ├─ LLM推理前，规则引擎检测紧急关键词
  ├─ 检测到 → InputCheckError终止Agent循环 → 直接返回急救指导
  └─ 零LLM消耗，零漏检

第2层 [指令强化] 系统提示词
  ├─ "你是健康助手，不是医生"
  └─ "不能提供诊断结论或用药建议"

第3层 [后置钩子] MedicalSafetyGuardrail
  ├─ 输出正则匹配：拦截"诊断为/确诊/建议用药/处方"等9-12个模式
  ├─ 患者端替换："小安不能提供诊断或用药建议"
  └─ 医生端替换："AI辅助生成，不构成确定性诊断，需医生审核"
```

第一层拦截紧急输入（8个紧急关键词 + 4个自杀风险关键词），不消耗LLM资源；第二层贯穿推理过程，引导合规输出；第三层拦截越界输出（患者端9个模式、医生端12个模式）。

### 3.5 确定性规则引擎（CPU）

13条规则覆盖3个领域：

| 领域 | 规则数 | 示例规则 | 级别 |
|------|--------|---------|------|
| 生命体征 | 8 | 收缩压 $\geq 140$ 或舒张压 $\geq 90$ | RED |
| 胎儿 | 2 | 胎动 $<$ 7日均值 $\times 0.5$ | RED |
| 心理 | 3 | 情绪评分均值 $\geq 8$ | ORANGE |

规则引擎采用自定义安全求值器（避免`eval()`），支持`and`/`or`/`not`逻辑运算和6种比较运算符。每领域仅返回最高优先级命中。支持热更新，延迟 < 1ms。

### 3.6 RAG知识增强

系统设计了基于BGE-M3嵌入模型的RAG管线。当前版本中，嵌入模块以mock模式运行（SHA256伪向量），配合SQLite的关键词回退搜索实现基础检索功能。生产部署时切换为BGE-M3本地推理（FP16，GPU）+ pgvector余弦相似度检索。

- **离线**：文档分块 → BGE-M3嵌入（规划：FP16，GPU） → pgvector索引
- **在线**：用户提问 → 嵌入 → ANN检索Top-3 → Prompt组装 → LLM生成
- **知识库**：3个核心文档（营养指南、产检说明、并发症处理），支持增量更新

## 4 硬件利用与优化策略

### 4.1 平台规格

| 组件 | 规格 | 角色 |
|------|------|------|
| CPU | AMD Zen5, 16核 | 调度/规则/API/DB |
| GPU | Radeon 8060S (RDNA 3.5) | LLM推理 |
| NPU | XDNA 2, 50 TOPS | FGR评估 |
| 内存 | 128GB LPDDR5x UMA | 共享，GPU最大96GB |

**UMA关键优势**：CPU-GPU数据拷贝延迟从 $\sim 10 \text{-} 50\,\mu s/\text{GB}$（PCIe分立显卡）降至零（同一物理地址），模型一次加载全局可访问。

### 4.2 异构任务分配

| 任务 | 执行单元 | 理由 |
|------|---------|------|
| LLM推理 | GPU | 矩阵乘法密集，SIMD并行 |
| FGR推理 | NPU | 固定结构，低功耗专用加速 |
| NLU意图识别 | CPU | 规则引擎，正则匹配，延迟<1ms |
| 规则引擎 | CPU | 控制流密集，确定性计算 |
| 任务调度 | CPU | I/O密集，复杂逻辑 |

### 4.3 内存分配（128GB UMA）

| 区域 | 分配 | 内容 |
|------|------|------|
| 系统保留 | ~8GB | OS + 驱动 |
| GPU推理区 | ~45GB | LLM Q8(35GB) + KV Cache预留(30GB) |
| NPU推理区 | ~2GB | FGR FP16(0.5GB) + 预留(1.5GB) |
| CPU工作区 | ~45GB | FastAPI(2GB) + PostgreSQL(8GB) + Redis(4GB) + 弹性(20GB) |
| **总计** | **~100GB** | **/ 128GB** |

### 4.4 量化策略

**当前已部署的模型：**

| 模型 | 原始格式 | 量化方案 | 部署大小 | 部署位置 | 状态 |
|------|---------|---------|---------|---------|------|
| LLM (Qwen3.6-35B-Q8-VL) | GGUF Q8-VL | Q8_0 (llama.cpp内置) | ~35GB | GPU (llama-server) | 已部署 |
| FGR (ResNet18DualFusion) | PyTorch FP32 | ONNX FP16 + INT8(可选) | ~0.5GB | NPU/GPU/CPU (ONNX Runtime) | 已部署 |

**规划中尚未部署的模型：**

| 模型 | 规划精度 | 规划方案 | 预估大小 | 目标位置 | 状态 |
|------|---------|---------|---------|---------|------|
| Embedding (BGE-M3) | FP16 | 不量化 | ~1.2GB | GPU | 代码就绪，配置为mock模式 |
| NLU意图 (BERT-base) | FP32 | ONNX INT8 | ~0.1GB | NPU | 未实现，当前为规则引擎 |
| NLU情感 (BERT-tiny) | FP32 | ONNX INT8 | ~0.03GB | NPU | 未实现，当前为关键词计数 |

**说明**：本地LLM实际使用`qwen3.6-35b-q8-vl`模型，通过llama.cpp的llama-server以OpenAI兼容API提供服务。该模型为Qwen3.6-35B密集模型的Q8量化视觉-语言变体，非MoE架构的A3B版本。云端对比实验使用的是Qwen3.6-35B-A3B（MoE，35B总参/3B激活），通过DashScope API调用。FGR模型的INT8量化通过AMD Quark工具链完成（XINT8方案），校准数据为全训练集，验证量化前后输出sigmoid概率差异 $\leq 0.05$。

### 4.5 ONNX硬件后端降级链

```
首选: VitisAIExecutionProvider (NPU)
  ↓ 不可用
备选: MIGraphX / ROCMExecutionProvider (GPU)
  ↓ 不可用
兜底: CPUExecutionProvider (CPU)
```

自动检测`ort.get_available_providers()`，结果LRU缓存。模型加载优先选INT8版本（`*_int8.onnx`），不存在则回退FP32。

### 4.6 性能优化技术

| 技术 | 作用 |
|------|------|
| KV Cache预分配 | 避免运行时内存分配抖动 |
| 模型预热 | 启动时空推理，触发首次编译缓存 |
| Prompt缓存 | 系统提示词GPU侧缓存，减少重复预填充 |
| 流水线并行 | CPU NLU与GPU LLM预填充重叠执行 |
| 持续批处理 | 多用户请求动态合并，提高GPU利用率 |

### 4.7 故障降级策略

| 故障场景 | 降级方案 | 影响 |
|---------|---------|------|
| GPU不可用 | LLM → CPU后端 | 延迟增至10-15s |
| NPU不可用 | FGR → CPU ONNX Runtime | FGR延迟增至20-30s |
| UMA不足 | 卸载对话模型 | 情绪陪伴降级 |
| 全部故障 | 兜底话术 | 服务降级不中断 |

超时配置：LLM 5s/2次重试 → 规则引擎响应；FGR 8s/1次重试 → 返回上次结果；NLU 500ms/2次重试 → 默认通用意图。

## 6 行业应用价值与落地分析

### 6.1 临床价值

**筛查效率**：FGR评估模型提供系统化图像分析+置信度分层，减少主观偏差。5折集成推理确保评估可靠性。

**护理减负**：随访准备从30-60分钟/人降至秒级AI生成。以每名护士管理80名孕妇、每周随访20名计算，AI辅助可每周节省10-20小时。

**患者体验**：$7 \times 24$小时RAG知识问答+CBT情绪陪伴+紧急零延迟检测。

**三端闭环**：孕妇数据 → 规则引擎 → 护士审核 → 医生诊断 → 医嘱回传，消除信息传递延迟和遗漏。

### 6.2 端侧部署必要性

| 维度 | 云端方案 | 端侧方案 |
|------|---------|---------|
| 隐私 | 数据外传风险 | 数据不出端 |
| 网络 | 依赖连接 | 离线可用 |
| 延迟 | 含网络传输 | 零传输延迟 |
| 成本 | 按Token持续计费 | 一次性硬件投入 |

### 6.3 方案可复制性

- **Agent架构**可推广至慢病管理、术后康复、心理健康等场景
- **ONNX Runtime**跨平台，异构方案可迁移至Intel/Qualcomm/Apple平台
- **三层安全防护**与具体模型无关，可移植至任何医疗AI场景

### 6.4 局限与展望

**局限**：FGR准确率0.701尚不足以支持临床决策；知识库仅3个文档；NLU为规则引擎，复杂语句理解有限；本地吞吐在多用户并发下可能瓶颈。

**方向**：医学微调LLM + 更大FGR数据集；NPU端BERT替代规则NLU；语音交互（FunASR + CosyVoice）；多模态融合（影像+临床文本）；联邦学习跨院泛化。

## 7 结论

AI-Care在AMD Ryzen AI Max+ 395上实现了端侧孕期管理Agent系统的全链路本地化运行：

1. **异构协同**：GPU（LLM推理）+ NPU（FGR评估）+ CPU（调度+规则+NLU），UMA零拷贝
2. **多Agent协作**：三端15个变体，16个工具，意图驱动路由，2个工作流
3. **安全防护**：确定性前置检测（零LLM消耗）+ 指令强化 + 输出模式匹配
4. **端侧性能**：TTFT 0.34s，吞吐53.70 tok/s，功耗 $\leq$ 120W，数据不出端
